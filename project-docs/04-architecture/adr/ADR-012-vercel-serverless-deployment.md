# ADR-012: Vercel serverless deployment (backend, web, admin)

Status: **Accepted 2026-11-20** (client decision, SRC-007.1; replaces the earlier "Option A" answer) · **Supersedes ADR-005** · Amends ADR-011 (cookies, cron) · Resolves B-017, B-021 and the `TRUST_PROXY` / `CRON_SECRET` questions.

## Context
All three apps deploy on Vercel. Stated platform facts (client, SRC-007.1; re-verify against the Vercel docs and the chosen plan before go-live): Vercel Functions support WebSockets natively (GA, Fluid Compute); Socket.IO works when the client uses `transports: ['websocket']`; a connection is closed at the function duration limit (about 5 minutes by default); Vercel runs many instances at once. ADR-005 assumed one long-lived instance, in-memory rate limiting and no adapter. None of that holds, and Redis stays out of scope.

## Decision

### 1. Functions
- **API function** `backend/api/index.ts` exports the Express app (`export default app`). `vercel.json` rewrites every path except the socket path to it. Base path stays `/api/v1`; health is `GET /health`. **Amended 2026-11-23 (T-026):** Vercel's backend-framework routing now invokes functions with `req.url` set to the rewrite *destination* path, so the rewrites carry the requested path in the `__originalPath` destination query and the app (first middleware) and the socket function (upgrade listener) restore it via `src/lib/vercelUrl.ts` — a no-op under local dev and the old routing behaviour. The function compiler also type-checks package imports with the require-condition view even in ESM files; `npm run build:vercel` (`scripts/vercel-typecheck.mjs`) replicates that resolver so a dual-published package that only breaks on Vercel (helmet needed a `paths` pin to its ESM types in `tsconfig.json`) is caught locally.
- **Socket function** `backend/api/socket-io.ts` runs the Socket.IO server with `path: '/api/socket-io'`, `addTrailingSlash: false`, `transports: ['websocket']` and CORS = `CORS_ALLOWED_ORIGINS` (credentials). Its own function so connection lifetime and duration limits do not affect the API. **Amended 2026-11-23 (T-026, preview verification):** the function **default-exports an `http.Server`** with Socket.IO attached — the official Vercel WebSocket shape (`vercel.com/docs/functions/websockets`) — and the websocket upgrade reaches it **without any rewrite**. No rewrite may match the socket path: upgrade requests pass through rewrites BEFORE upgrading (same doc), so the earlier `/api/socket-io/(.*)` rewrite moved the upgrade away from the engine.io path and the connection never upgraded (preview-check step 3 "websocket error"). The API catch-all therefore excludes the subtree: `"/((?!api/socket-io).*)" → "/api/index?__originalPath=/$1"`, locked by a conformance test. **Amended again 2026-11-23 (preview evidence):** Vercel routes **only the exact function path** `/api/socket-io` to the function — sub-paths such as `/api/socket-io/socket.io/` get the platform 404 (`GET /api/socket-io` → 200 reached the function, `GET /api/socket-io/socket.io/?EIO=4&transport=polling` → platform `NOT_FOUND`), so the earlier "routes `/api/socket-io/*`" claim was wrong for this deployment. Socket.IO therefore serves the function path itself: server and every client use `path: '/api/socket-io'` with `addTrailingSlash: false` (Socket.IO ≥ 4.6), making engine.io requests `/api/socket-io?EIO=…`. Consequence: engine.io owns the exact path, so a GET without an `EIO` query is answered by engine.io with 400 `{"code":0,"message":"Transport unknown"}` — that response **is** the reachability probe. The wire path is locked by tests (exact upgrade URL recorded from a real client; the retired `/api/socket-io/socket.io` path asserted unused and still excluded from the catch-all).
- Local dev still runs one Node process (`npm run dev`) that mounts both on port 4100; the code is the same, only the entry differs.

### 2. Cross-instance delivery without Redis
- Socket function: `@socket.io/mongo-adapter` on collection `socket.io-adapter-events` (name from env `SOCKET_ADAPTER_COLLECTION`).
- REST API (any instance): `@socket.io/mongo-emitter` writes to the same collection, so `emitter.to('user:{id}').emit('notification:new', n)` and `emitter.to('admins').emit(...)` reach whichever instance holds the socket.
- **Collection type: TTL, not capped.** The collection is created with `createdAt` stamped on each document (adapter option `addCreatedAtField: true`) and a TTL index `{createdAt: 1}, expireAfterSeconds: 3600`. Reason: documents in a capped collection cannot be deleted, which would defeat the cron cleanup below; a TTL collection can be swept by both the TTL monitor and the cron job. The adapter reads new documents with a change stream (Atlas is a replica set, so this works). **T-023 starts with a spike test on the chosen Atlas tier** (adapter + emitter across two server instances); if the tier rejects it the fallback is a capped collection and the cron step skips it. **Atlas change streams verified on the dev cluster, 2026-11-22** (owner ran `scripts/spikes/atlas-change-stream.ts`: TTL index created, change stream delivered in 292 ms, emitter → adapter → socket across two instances in 158 ms, `SPIKE PASS`); the capped-collection fallback is not needed.
- The Notification row in MongoDB remains the source of truth. Emitting is best effort: a failed emit is logged and never fails the REST request.
- Native `mongodb` driver client: one singleton per instance (`src/lib/mongo.ts`, `maxPoolSize` 2) shared by the adapter and the emitter; same `DATABASE_URL` as Prisma.

### 3. Client behaviour (web and admin)
- `io(SOCKET_URL, { path: '/api/socket-io', addTrailingSlash: false, transports: ['websocket'], reconnection: true, reconnectionDelay: 1000, reconnectionDelayMax: 15000, randomizationFactor: 0.5 })` with no attempt limit (path + `addTrailingSlash` amended 2026-11-23: Vercel routes only the exact function path, see §1).
- `auth` is a callback: before every (re)connect it returns a fresh access token (refresh first if it expires within 60 s). An `unauthorized` connect error triggers one refresh and one retry; a second failure logs the user out.
- On **every** `connect` (first and re-connect): re-fetch `GET /notifications` (page 1; the response already carries `unread`), then update the bell. Notifications newer than the last one the user saw get a toast (grouped as "N new notifications" when more than 3). The planned close at the duration limit is therefore invisible except for a short reconnect.
- Required test (NOTIF-01/02/03): *a notification created while the socket was disconnected is shown after the reconnect* (backend/web/admin).

### 4. Rate limiting (replaces in-memory)
- `express-rate-limit` with a custom MongoDB store, plus a reusable `hit(key, limit, windowSeconds)` helper for counters that are not per request IP (e.g. login failures per email, T-005). Collection `RateLimit {key (unique), hits, resetAt}`. Each hit is **one atomic `findAndModify` upsert with an update pipeline** (not a plain `$inc`): a plain `$inc` cannot reset an expired window atomically, and the TTL monitor only runs about once a minute, so an expired document can still exist. The pipeline sets `hits = 1, resetAt = now + window` when the document is new or `resetAt <= now`, otherwise `hits = hits + 1`. If two instances create the same key at once, the loser gets a duplicate-key error (E11000) on the unique `key` and retries once, which takes the update path. A TTL index `{resetAt: 1}, expireAfterSeconds: 0` removes finished windows. It is created at start-up (and lazily on first use on serverless) by an idempotent, memoized `ensureIndexes()` (`$runCommandRaw`) because Prisma cannot declare TTL indexes (and must not declare a plain index on the same key).
- Keys: `rl:{scope}:{kind}:{id}` (`login:ip:<ip>`, `login:email:<hmac>`, `otp:email:<hmac>`). The IP is `req.ip` only (Express applies `TRUST_PROXY`; with `TRUST_PROXY=false` the forwarded header is ignored; with `1` it comes from the Vercel-set header). IPv6 is reduced to its /64 prefix and IPv4-mapped IPv6 to plain IPv4. Emails are lowercased, trimmed and HMAC-SHA256'd with `REFRESH_TOKEN_PEPPER`, so a leaked collection cannot be reversed with a list of known emails. If the store is unreachable the limiter fails open, logs an error with the request id and never crashes the request (availability over blocking); the per-account lockout (ADR-011) still protects login.
- Login lockout already lives on `User` and is unchanged.

### 5. Cron
- Vercel Cron (`vercel.json` `crons`) calls **`GET /internal/cron/cleanup`**. Vercel Cron always issues `GET` and, when the project env `CRON_SECRET` is set, adds `Authorization: Bearer <CRON_SECRET>`; it cannot add custom headers. The route therefore accepts **either** `Authorization: Bearer <CRON_SECRET>` **or** `x-cron-secret: <CRON_SECRET>` (manual runs, other schedulers), on `GET` or `POST`. Constant-time comparison; missing/wrong secret → 401; `CRON_SECRET` unset → route not mounted.
- Cleanup deletes: OTPs expired or consumed; refresh tokens expired or revoked; Socket.IO adapter documents older than `SOCKET_ADAPTER_TTL_SECONDS`; read notifications older than 90 days and unread ones older than 180 days (owner, 2026-11-22, added with T-016); `Upload` rows never attached after 24 h, with their R2 object, max 200 per run (owner, 2026-11-21 — supersedes the earlier "orphaned R2 uploads cleanup stays out of scope" line; an R2 object referenced by an order item's `imageKey` is never deleted, and a failed R2 delete keeps the row for the next run). Response `{ otps, refreshTokens, socketEvents, uploads, notifications }` counts. Idempotent and safe to run twice.
- Schedule `0 3 * * *` (daily, allowed on every Vercel plan; hourly needs Pro). OTP expiry is enforced at verification time, so cleanup frequency affects storage only. This replaces the `node-cron` plan and the "startup + hourly" cleanup.

### 6. Proxy, Prisma, Atlas
- `TRUST_PROXY=1` in production (Vercel is the single proxy hop); `false` locally.
- Prisma: one `PrismaClient` per instance via a `globalThis` singleton (`src/lib/prisma.ts`), also in development to survive hot reload. No `$disconnect()` per request.
- Atlas connection settings (append to `DATABASE_URL`, tune per plan; verify the options with Prisma 6 at T-001): `maxPoolSize=5`, `minPoolSize=0`, `maxIdleTimeMS=60000`, `serverSelectionTimeoutMS=5000`, `retryWrites=true&w=majority`. **Connection budget** = running instances × (Prisma pool + driver pool of 2). Atlas M0 allows 500 connections, M10 1 500; with Fluid Compute many concurrent requests share one instance, so the real count is low, but monitor it. Atlas network access: Vercel has no fixed egress IPs on the standard plan, so the Atlas IP access list allows `0.0.0.0/0` protected by a strong DB user password (or use Vercel's static IPs / private link on a paid plan).
- Cold start: Prisma client generated at build (`prisma generate` in `postinstall`, `binaryTargets` includes the Vercel runtime target); env validation runs once per instance.

### 7. Mail and local dev (SRC-007.4)
Atlas (a dev cluster or database) and Gmail SMTP are used in development as well; Docker is no longer required. Gmail SMTP: `smtp.gmail.com`, port 587, account with 2-step verification and an app password in `SMTP_PASS`; `MAIL_FROM` must be that address or a verified alias. Gmail limits sending volume (roughly 500 messages/day on a free account), enough for the MVP OTP and order emails; move to a transactional provider before launch volume (B-005 note). Tests do not use SMTP (Nodemailer `jsonTransport`) and use `mongodb-memory-server` (replica set).

## Consequences
- ADR-005 is superseded: no in-memory limiter, no single-instance rule; still **no Redis, Kafka or queues**. Emails are still sent in-process; on serverless a response must not finish before the send is awaited, so order emails are awaited with `waitUntil` from `@vercel/functions` (or awaited directly), not fire-and-forget.
- Domain events stay an in-process `EventEmitter` inside one request; fan-out to other instances goes through MongoDB (adapter collection), not memory.
- New dependencies: `@socket.io/mongo-adapter`, `@socket.io/mongo-emitter`, `mongodb`, `@vercel/functions`. New tasks T-023 (adapter and emitter), T-024 (rate-limit store), T-025 (cron route), T-026 (Vercel config). T-016 now depends on T-023.
- NOTIF-01's "within 2 s" holds while the socket is connected; during a reconnect the unread-count/list re-fetch closes the gap (new acceptance criteria and tests).
- Risks: duration-limit and plan limits for WebSocket functions (verify), Atlas connection counts. Change-stream support on the chosen Atlas tier was verified by the T-023 spike on the dev cluster (2026-11-22); re-run `scripts/spikes/atlas-change-stream.ts` only if the cluster or tier changes.
