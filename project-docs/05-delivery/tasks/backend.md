### T-005 Login, refresh, logout, me, auth/role middleware · done
- Req: AUTH-02, AUTH-05, AUTH-06 · Depends: T-004, T-024
- Note: depends on T-024 (MongoDB rate-limit store) because the AUTH-02 IP rate-limit test (10 failures / 15 min / IP -> 429) needs it. Do T-024 first. No stub admin route in production code for AUTH-06: decided, see requirement 6 (`createApp({ extraRouters })`, test-only admin router).
- Security requirements (approved by the client owner 2026-11-21; apply when T-005 starts; update `api-spec.yaml` first: `INVALID_CREDENTIALS`, `REFRESH_RACE`, JWT claims note):
  1. **No account enumeration.** Unknown email and wrong password both -> identical 401 `INVALID_CREDENTIALS` (same body). Unknown email runs a dummy argon2 verify (timing). `EMAIL_NOT_VERIFIED` and `ACCOUNT_BLOCKED` are returned only after the password verifies; otherwise the generic 401. **Lockout (corrected 2026-11-21, supersedes the first wording):** order is IP limiter -> email lockout check -> find user (or dummy argon2) and verify the password -> status checks. While the email is locked, EVERY attempt gets 429 `ACCOUNT_LOCKED` BEFORE any password check, for known and unknown emails alike (a 429 only on a correct password would be a password oracle). The T-024 key `login:email:<hmac>` (`hit`, `peek`, `extendWindow`) is the single source of truth; `User.failedLoginCount` (atomic `increment`) and `lockedUntil` are only a mirror for admins. A failure hits the key and returns the generic 401; the lockout lasts `LOGIN_LOCKOUT_SECONDS` from the failure that reached the limit; success resets the key. Tests: `AUTH-02 · unknown email and wrong password return identical 401`, `AUTH-02 · blocked/unverified status is not revealed with a wrong password`, `AUTH-02 · during lockout a correct password also gets 429 (no password oracle)`, `AUTH-02 · lockout behaves identically for known and unknown emails`.
  2. **`requireAuth` loads the user from the DB on every request**; 401 if missing or blocked; `role` comes from the DB, not only the JWT. Tests: `AUTH-06 · a blocked user's still-valid access token is rejected`, `AUTH-06 · role downgraded in DB takes effect immediately`.
  3. **Refresh concurrency, 10 s grace window.** A just-rotated token presented again within 10 s -> 401 `REFRESH_RACE`, family NOT revoked, client retries with the new cookie. Reuse after the window revokes the whole session family (`RefreshToken.familyId`, set at login and kept across rotations); all of a user's tokens are revoked only on password reset and block (`revokeAllForUser`, used by T-006/T-017). Tests for both. The CSRF token is `HMAC(CSRF_SECRET, familyId)` (survives rotations); `GET /auth/csrf` needs a live refresh cookie (401 otherwise); a present `Origin` not in `CORS_ALLOWED_ORIGINS` -> 403 `CSRF_INVALID`; Bearer-only requests are exempt. Tests: `AUTH-05 · CSRF token stays valid after a refresh rotation`. Add a note to web T-031 and admin T-061: refresh must be single-flight (one in-flight refresh shared by all requests).
  4. **JWT.** Verify with `algorithms: ['HS256']`; set and verify `iss` "furnixa-api" and `aud` "furnixa"; claims `sub`, `role`, `jti`. Test: tokens signed with `none` or another secret are rejected.
  5. **Atomic counters.** `failedLoginCount` uses an atomic `increment`, never read-then-write. The session-cap revoke happens in the same transaction as creating the new `RefreshToken`.
  6. **No admin stub in production code** (no `/admin/ping`). `createApp({ extraRouters })`; tests mount a test-only admin router behind the real `requireAuth` + `requireRole('ADMIN')` to test AUTH-06.
- Docs: `PRD#5.1`, `roles-permissions.md`, `adr/ADR-003`
- Carried over from T-024: a login-level test named `AUTH-02` for "10 failed attempts in 15 min from one IP -> 429" (T-024 proves the limiter only, under `NFR-01`).
- Done: tests for unverified login, blocked login, rate limit, refresh rotation + reuse detection, customer → admin route = 403. Tests named `AUTH-02`/`AUTH-05` (ADR-011): argon2id hash verifies; `LOGIN_MAX_FAILURES` failures → 429 `ACCOUNT_LOCKED` until `LOGIN_LOCKOUT_SECONDS` pass (use fake timers), success resets the counter; login number `MAX_ACTIVE_SESSIONS`+1 revokes the oldest session; refresh TTL is `REFRESH_TOKEN_TTL_SECONDS`; `/auth/refresh` and `/auth/logout` without/with bad `X-CSRF-Token` → 403 `CSRF_INVALID`, with a valid one → success; cookie flags follow env.

The submitted password is matched (argon2 verify) against the unexpired `pendingRegistration.passwordHash` rows of the email, and the new OTP is bound to the matching row only. No match -> the generic 401 `INVALID_CREDENTIALS` (counted as a failed login); **no decoy OTP row is written** (login answers identically for every miss, so there is nothing to disguise). A correct password inside the OTP cooldown / hourly cap still returns 403 `EMAIL_NOT_VERIFIED` but sends no mail (a 429 there would reveal the password was right).
